# 成本 · 延迟 · Token 用量披露

> `docs/submission_rules.md` 要求提交"a disclosure of latency, token usage, and estimated model cost"，
> `docs/competition_specification.md` 说明这属于 **Feasibility 评分项**（不进 TechnicalScore）。
> 本文件是那份披露。数据源在 M3（`llm_client.pop_usage()`），故归 C 维护。
>
> 测量环境：Apple M5 / 10 核 / 24 GB / Python 3.12.13 / macOS 26.6。全部为本机实测，非估算。

## 一句话结论

**默认配置在公开卷上不产生任何模型调用：0 token、0 费用、断网出分不变，200 条会话全量评测约 10 秒。**
08-31 起 `LLM_PARSE=1` 成为默认，但它是**增强模式而非依赖**——只在规则解析失手时才醒来，
而公开卷上规则从未失手（`llm_calls = 0`，分数与 `LLM_PARSE=0` 逐位相同）。
无凭证或断网时连续 2 次失败即熔断、退回纯规则路径，**headline 数字不变**。
排序侧 LLM（`USE_LLM=1`）与稠密路（`USE_DENSE=1`）仍默认关闭。

## 默认提交配置（`USE_LLM=0` `LLM_PARSE=1` `USE_DENSE=0`）

| 指标 | 实测 |
|---|---|
| 第三方依赖 | **无**（纯 Python 标准库，`requirements.txt` 里的包只有 `USE_DENSE=1` 才需要） |
| 网络调用 | **公开卷上为 0**（断网跑 `python3 -m evaluator.local_evaluator` 得分逐位相同） |
| Token 用量 | **0**（公开卷零触发；改写场景下的实测见下节） |
| 模型费用 | **¥0** |
| 启动耗时 | 4.1 ~ 6.9 秒（一次性：加载 5 万商品 + 建 SQLite FTS5 索引） |
| **常驻内存（RSS）** | **340 MB**（macOS `ru_maxrss`，含 SQLite）／ **530 MB**（Windows 峰值工作集，@周峻恺 实测）。跑完 50 会话 × 3 轮后 341 MB —— **无泄漏**。跨平台差异来自两套口径与分配器行为，报告以较保守的 530 MB 为准 |
| ~~启动内存峰值 162 MB~~ | ⚠️ **旧数字已作废**：那是 `tracemalloc` 的 Python 侧口径，**不含 SQLite 自身内存**，低估了一半以上。以上面的 RSS 为准 |
| 单轮 `respond()` 延迟 | **中位 2.3 ms ／ p95 2.8 ms ／ max 3.5 ms**（60 次采样） |
| 全量 200 条会话 | **9.7 秒**（含启动） |
| TechnicalScore | **0.946642**（HitRate 1.000 / MRR 0.884 / MTTC 1.935） |

单轮延迟中位 2.3 ms —— 官方保留"超时记 miss"的权利，这个量级下超时风险可以认为不存在。

## 可选增强一：LLM listwise 精排（`USE_LLM=1`，默认关）

模型：GLM-4.7-Flash（智谱，永久免费）。客户端 `src/ranking/llm_client.py`，纯 stdlib `urllib`，
`thinking` 显式关闭、JSON 模式、`temperature=0`、失败重试一次、任何异常回落规则序。

抽样 40 条（`--n 40 --seed 2026`，四场景比例严格保持）实测：

| 配置 | Score | MRR | 单次调用延迟 | Token（40 条） | 全量 200 条推算 |
|---|---|---|---|---|---|
| 纯规则（对照） | **0.9507** | 0.963 | — | 0 | 10 秒 ／ ¥0 |
| `LLM_PROMPT=basic` | 0.9305 ↓ | 0.905 ↓ | ~2.2 s | 18,675 | 约 16 分钟 ／ 9.3 万 token |
| `LLM_PROMPT=evidence`（默认形态） | 0.9503 | 0.963 | ~2.3 s | 20,423 | 约 18 分钟 ／ 10.2 万 token |

evidence 臂跑 3 次取均值：**0.9511 (±0.0005)** —— 与纯规则 0.9507 的差异在方差带内。

**费用**：GLM-4.7-Flash 免费额度内 **¥0**。若换 DeepSeek v4-flash 闲时价（¥1.5/¥4.5 每百万 token），
全量一次约 **¥0.18**；整个开发期跑 30 次也不到 ¥6。

**结论**：开启 LLM 精排要付出 **~100 倍延迟**（9.7 秒 → 18 分钟），换来的是统计上的零收益。
故 `USE_LLM` 默认 0。详见 [experiments.md](experiments.md) 的 C-T9 系列（实验 25 / 25a-25c）。

> ⚠️ 附带的可复现性代价：LLM 路径分数**不可复现**（`temperature=0` 下服务端仍有波动，
> 实验 4c 已证实）。这意味着"改一行代码看分数"的开发方式在该路径上失效——
> 这本身就是不把它设为默认的理由之一。
>
> ⚠️ **静默降级是真会发生的**：C-T9 复跑第 2 次 `tokens=0`、分数恰好等于纯规则基线——
> 所有调用超时失败后回落规则序，且**没有任何报错**。根因是 `LLM_TIMEOUT` 原设 20 秒，
> 而 GLM 免费额度单次调用实测可达 **21.5 秒**。已改为 45 秒。
> 这件事本身说明了为什么主路径不能依赖外部模型：它会在你不知情的时候消失。

## 默认增强：LLM 逐字片段抽取（`LLM_PARSE=1`，08-31 起默认开）

M1 的第三层解析防线：仅在严格模板与规则载荷抽取都落空时触发，且 LLM 产出必须通过
**verbatim 校验**（归一化后是原消息的连续子串，改写/编造一律丢弃）。无 key 秒降级，
连续 2 次失败熔断。

**收益**（experiments.md #41，全量 200 会话 × 五档，一档一进程）：

| 压力档 | 纯规则 | 开 `LLM_PARSE` | 增量 | 触发次数 |
|---|---|---|---|---|
| L0 原文 | 0.940829 | 0.940829 | **±0（零触发）** | **0** |
| L1 换句式 | 0.922250 | 0.936189 | +0.0139 | 124 |
| L2 短语改写 | 0.887364 | 0.923139 | +0.0357 | 265 |
| L3 规格串重组 | 0.869587 | 0.929689 | +0.0601 | 334 |
| L4 无冒号口语 | 0.814278 | 0.911811 | **+0.0975** | 386 |

L3/L4 的 HitRate@10 从 0.955 / 0.920 双双回到 **1.000 / 0.995**，L4 的 MTTC 从 2.735 降到 2.045。

**成本实测**（跑满五档 = 最坏情况；外部计量与 evaluator 自报 `reported_token_usage` 逐档相等）：

| 项 | 实测 |
|---|---|
| 总调用 | 1109 次（L0=0 / L1=124 / L2=265 / L3=334 / L4=386），0 次失败，熔断从未触发 |
| Token | prompt 186,525 + completion 27,725 = **214,250** |
| 预估费用 | **¥0.13 ~ ¥0.39**（区间源于前缀缓存命中率未知，上界按缓存全未命中计） |
| 单次调用延迟 | mean 0.72 ~ 1.18 s ／ p95 1.0 ~ 5.6 s |
| **实际计分场景** | 私有卷为 L0 等价 ⇒ **零触发、零 token、零费用** |

> ⚠️ **超时尾部风险**：观测到一次调用撞满 `LLM_TIMEOUT=45s`（max 45.86 s）后内部重试成功。
> 官方保留"超时记 miss"的权利，而正常调用中位数仅 0.7–0.8 s——建议给解析层单独设更短超时
> （几秒即可覆盖 p95），把最坏单轮延迟从 46 s 压到个位数秒。
>
> 📌 **可精确化**：`src/ranking/llm_client.py` 目前只累计 `prompt_tokens` / `completion_tokens`，
> 未记录 API 返回的 `prompt_cache_hit_tokens`。补一行即可把上面的费用区间收敛成精确值。

## ⚠️ 关于官方的资源限制

`submission_rules.md` 原文：*"The organizer reserves the right to run your submission under CPU,
memory, timeout, and network restrictions."* —— **保留了权利，但没给具体数值**。我们是在不知道
限额的情况下设计的，所以按"越省越安全"取舍：

| 配置 | 常驻内存 | 依赖 | 网络 |
|---|---|---|---|
| **默认（USE_DENSE=0）· 提交配置** | **530 MB** | 无（纯标准库） | 无 |
| `USE_DENSE=1`（**已决定不启用**） | **1191 MB** | torch + transformers + sentence-transformers | 无（离线只读缓存） |

以上为 @周峻恺 在 Windows 上的实测峰值工作集（全量 200 条，子进程 `K32GetProcessMemoryInfo` 口径）。
**+661 MB 的增量几乎全是 torch / transformers 运行时本身** —— npz 向量矩阵只占其中 77 MB。
（commit 峰值达 2.8 GB，那是 torch 的虚拟预留，分页前不计入实际占用；但若限额按 commit 计算会更糟。）

**决定：提交配置取 `USE_DENSE=0`。08-31 更新：这条决定的理由已经从"赔率"升级成"实测为负"。**

原论证（仍然成立、但已不是主因）：稠密路在 `EARLY_TOPK=1` 下收益 **+0.0016**（0.9694 → 0.9710），
低于我们自己定的 0.002 噪声阈值——不能一边用该阈值否掉实验 12b 的 +0.0009，一边为同量级收益
去换一条新的运行时失败路径。（@BestBucky，留言板 T-014③）

**新论证（实验 37/38/42）**：撤销收窄藏牌后，稠密路在 L0 的收益**翻为 −0.0090**。插桩归因给出机制：
稠密候选带哨兵名次、只增加召回从不挤占，但"多出来的召回"让目标**提前一轮命中于平庸名次**，
而"命中即终局"把该名次锁死——L0 上 18 条变化会话里 17 条提前命中、11 条名次变差、**0 条**从脱靶被救回。
藏牌正是挡住这条伤害通道的盾（早轮不暴露 3–6 名候选），它一撤，收益就翻号。
再叠加 `LLM_PARSE=1` 之后，上游解析被修好、BM25 召回恢复，反事实从"根本不命中"退回"晚一轮但排第 1"，
稠密路在**五档全负**（−0.0065 ~ −0.0106）。
我们还实测了两种补救——逐字饱和条件放行、以及"精确筛+模糊排"的逐约束路由 + 只排不召：
两者都能把 L0 的下行完全消除，但在 LLM 开启后都无法转正（详见 experiments.md #40 / #42）。

稠密路的代码、预计算脚本与降级逻辑全部保留：它贡献了 **Recall@100 = 1.000** 的召回保险，
以及"资产缺失自动降级、行为逐字节一致"这条离线韧性叙事——两者都进报告与 demo。

## 可选增强三：稠密向量路（`USE_DENSE=1`，默认关）

bge-small-en-v1.5（133 MB 权重）预计算 5 万商品 embedding，产物 `data/embeddings.npz` **72 MB**，
运行期常驻内存约 73 MB（50k × 384 float32）。**无网络调用**（`TRANSFORMERS_OFFLINE=1`，只读本地缓存）。
需要 `requirements.txt` 里的 torch / sentence-transformers。

实测收益：0.9180 → 0.9272（实验 9，叠在热度先验之上）。
资产缺失或依赖未装时自动降级纯 BM25，行为与默认配置逐字节一致。

> ⚠️ **未决**：提交时 `USE_DENSE` 取 0 还是 1、72 MB npz 如何分发（留言板 T-004）。
> 取 0 则本项对最终分数贡献为零；取 1 则需确保评测方能拿到 npz 且能装上依赖。

## 我们为什么把 LLM 放在这个位置

三次控制实验的共同结论：

| LLM 用在哪 | 实测 | 结论 |
|---|---|---|
| **排序**（listwise 精排） | 喂标题 → **-0.020**；喂命中证据 → **±0.000** | 规则打分器已经把证据里的信号提取干净了，LLM 的天花板是"打平"，不是"超越" |
| **理解**（解析改写话术） | L4 压力档 **0.8330 → 0.9327** | 这是 LLM 真正不可替代的地方——规则写不出所有句式 |

也就是说：**LLM 在这个任务里应该用来"听懂"，而不是用来"排序"。**
这个判断不是先验的，是三组对照实验测出来的，每一组的原始数据都在 `team/experiments.md` 里。

## 复现

```bash
python3 -m evaluator.local_evaluator                                  # 默认配置，9.7 秒，0 token
USE_LLM=1 LLM_PROMPT=basic    python3 scripts/eval_sample.py --n 40   # 精排 basic 臂
USE_LLM=1 LLM_PROMPT=evidence python3 scripts/eval_sample.py --n 40   # 精排 evidence 臂
LLM_PARSE=1 python3 scripts/paraphrase_stress.py --levels L0 L4       # 解析第三层防线
USE_DENSE=1 python3 -m evaluator.local_evaluator                      # 稠密路（需 npz + 依赖）
```

API key 放 `.env`（已 gitignore，`scripts/check_guards.py` 会校验未入库）。
