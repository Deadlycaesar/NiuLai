## 三个决策输入

1. **T-004 数据链已闭环**：dense-on 收益 = 公开集 +0.0016（实验 #28）+ **改写档 L1 +0.011 / L3 +0.016**（O1 副产物，此前没人测过 dense-on 的压力档）——真实收益在鲁棒性轴；代价从 1191MB 降到 **787MB**（O10）。按 C 的标准（≤600 支持 / ≥1GB 反对），787 落在中间地带，但鲁棒性论据是新的。
2. **文本名次信号彻底封盘**：O2/O4/O5/O8 四个方向全部判平——bm25_rank 怎么调都不产生边际信息。以后任何人想动文本权重，先读这一页。
3. **召回侧没有剩余缺口**：O3/O6/O7 证明短语召回阈值、品类过滤、同义词扩展要补的对象都不存在（约束值产自目标自身元数据，逐字命中天然完备）。

## 明细

### O1 — dense 查询配方：slot.terms vs 原文拼接 ❌ 判平（已回滚）

- **假设**：归一化 terms 查询更干净 → dense-on 分数或压力档改善
- **改动**：`retriever._dense_query` 加 `DENSE_QUERY_MODE` 开关（raw/terms）
- **数字**（dense-on）：L0 raw=**0.9710** terms=**0.9710**；L1 均 **0.9614**；L3 均 **0.9058**——逐位相同
- **结论**：查询配方对结果零影响（与实验 7"稠密不是瓶颈"一致），回滚，`_dense_query` 维持原文拼接
- **⚠️ 副产物（重要）**：dense-off vs dense-on 的压力档对比——L1 **0.9501→0.9614**（+0.011）、L3 **0.8896→0.9058**（+0.016）。**稠密路的真实收益在鲁棒性轴，不在公开集**——这是 T-004 决策的新论据

### O2 — DENSE_TOP_K 扫描（50/100/200/300）❌ 不过验收线（纯环境变量）

- **假设**：更大的稠密补充池 → dense-on 正收益
- **数字**（dense-on L0）：50→0.9709 / **100→0.9710（现行默认）** / 200→0.9714 / 300→0.9713
- 峰值 200 的逐会话 diff：4↑0↓ 全是 MTTC 提前（+0.0004），看似方向性收益
- **但压力档双跌**：TOP_K=200 时 L1 0.9609 / L3 0.9042（vs TOP_K=100 的 0.9614 / 0.9058）——公开集涨、改写档跌 = 实验 10c 定义的过拟合拐点形态
- **结论**：维持默认 100。更深的稠密池捞进的是语义噪声候选，改写档下这些候选的指纹证据更弱

### O3 — 短语召回放宽（≥2 token + TOP_K 100）❌ 阴性（已回滚）

- **假设**：阈值放宽 → 改写档召回兜底更稳
- **改动**：`_phrase_recall` 加 `PHRASE_MIN_TOKENS` 开关，配合 `PHRASE_TOP_K=100`
- **数字**：L0 0.9694→**0.969275**（一条会话 RR 掉 0.0004，略损）；L1 **0.9501** / L3 **0.8896** 与基线逐位相同
- **结论**：阴性。≥3 token 阈值根本不是约束——L3 档连长规格串都被重组，2-token 短语同样活不下来；放宽只多捞噪声。维持 ≥3 + TOP_K=50

### O4 — BM25 列权重扫描 ❌ 判平（已回滚）

- **发现**：现行查询**已经有列权重**（`bm25(products, 0,6,4,2.5,2.5,1.5,1.0)`，title=6 最高）——假设的前提半错，实验退化为权重扫描
- **数字**：四组对照（平权 / title 拉满 / description 归零 / categories 最高）L0 全部 **0.9694 逐位相同**
- **结论**：BM25 名次的边际信息是零。排序打平局的胜负手在先验轴（实验 7/22 结论的再次独立验证：文本信号饱和后，怎么调文本权重都没用）。回滚，权重保持现状

### O5 — 稠密独有候选合成中段名次（40~100 插值）❌ 判平（已回滚）

- **假设**：高 sim 的稠密独有候选应得中段名次分，而非追加队尾记 0
- **改动**：`_fuse_dense` 加 `DENSE_INTERLEAVE` 开关，按稠密命中位次合成 bm25_rank
- **数字**（dense-on）：L0 **0.9710** / L1 **0.9614** / L3 **0.9058**——与队尾追加逐位相同
- **结论**：判平。稠密独有候选产生影响靠的是指纹 match_count 和先验，bm25_rank 那一点分（0 vs 中段）不改变任何胜负。队尾追加方案更简单，维持现状。**至此 bm25_rank 轴的三种玩法（列权重 O4 / 名次插值 O5 / 池深 O2）全部判平——文本名次信号确实被吃干净了**

### O6 — 粗品类软过滤 ❌ 判平/no-op（已回滚）

- **假设**：过滤跨类目噪声候选 → 排序更干净
- **改动**：`retrieve()` 加 `COARSE_FILTER` 软过滤（同类候选 ≥k 才生效，防误杀）
- **数字**：L0 **0.9694** / L1 **0.9501** / L3 **0.8896**——与基线逐位相同
- **结论**：过滤是事实上的空操作——查询本身已含品类词，BM25 池内候选几乎全部同类，没有"跨类目噪声"可滤。假设的对象不存在

### O7 — 同义词扩展进 slot.terms ❌ 阴性 no-op（已回滚）

- **假设**：评测器词表盖不住 navy/alloy 等具体取值 → 反向扩展泛词到具体词能补命中
- **改动**：`_expand_synonyms`（13 组词表、只加不换、≥4 字符护栏防 "tan"⊂"santa"），`SYN_EXPAND` 开关
- **数字**：L0 **0.9694** / L1 **0.9501** / L3 **0.8896**——三轴全部逐位相同；开关关闭回归确认 ✓
- **结论**：no-op，且**机理上注定是 no-op**——约束值抽取自目标商品自身元数据，目标必然逐字命中自己的约束；扩展只能给非目标加 match_count（加噪），加不到目标头上。这条路的假设对象不存在，关闭讨论

### O8 — CANDIDATE_POOL 扫描（600/1000）❌ 构造性 no-op（纯环境变量）

- **数字**：L0 两档均 **0.9694**；POOL=600 压力档 L1 **0.9501** / L3 **0.8896**，与基线逐位相同
- **结论**：可证明的空操作——`retrieve()` 在 SQL 拉完 CANDIDATE_POOL 条后立刻截断到 k=100，POOL 只影响哨兵值（子池归一化后映射为 0，与数值无关）。召回侧的"池深"旋钮在实验 22 之后已不存在，真正的池界是 k=100

### O9 — dense-on 下收窄参数重扫 ❌ 维持现状（纯环境变量，无改动）

- **假设**：稠密改变了早期轮的排序质量 → 「拿 MTTC 换 MRR」的汇率变化，27a 的结论可能失效
- **数字**（dense-on L0）：现行默认（TOPK=1/TURNS=3）**0.9710** ／ TOPK=0 → 0.9319 ／ TOPK=2 → 0.9575 ／ TURNS=2 → 0.9710 ／ TURNS=4 → 0.9710
- **结论**：**27a 在 dense-on 下完全成立**——TOPK=1 仍最优且领先巨大（-0.013~-0.039），TURNS 2/3/4 等价（hybrid 的 slots<4 先绑定）。无采纳改动 = 压力档即基线，不重复跑

### O10 — onnx-runtime 查询编码后端 ✅ 采纳（工程轴唯一胜场，commit 2eaaf12）

- **假设**：torch 运行时（+661MB）是 RSS 超支的全部原因 → onnx-runtime（~50MB 运行时）能在分数持平下把峰值压回
- **改动**：`dense.py` 拆出 `_torch_encoder` / `_onnx_encoder` 双后端（`DENSE_BACKEND` 开关，默认 torch 不变）；`_onnx_encoder` = tokenizers + onnxruntime，CLS pooling 与 ST 侧一致；`config.py` 加 `DENSE_BACKEND`/`EMBED_ONNX_DIR`/`EMBED_ONNX_MODEL`
- **向量 parity**：同一查询 torch vs onnx-fp32 余弦 **1.0000**（逐位等价）；onnx-int8（自量化 32MB）0.982
- **分数**（onnx-fp32，隔离 venv）：L0 **0.9710** / L1 **0.9614** / L3 **0.9058**——与 torch 后端逐位相同；int8 版 L0 同样 0.9710
- **RSS**（同口径 in-process 峰值工作集）：纯 BM25 **530MB** ／ torch 后端 **1191MB** ／ **onnx 后端 787MB**（int8 785MB——模型文件不是内存大头，onnxruntime 运行时本身才是）
- **结论**：采纳保留（开关默认 torch，零默认行为变化）。787MB 仍高于 600MB 支持线、低于 1GB 反对线——**T-004 的最终拍板数据链已完整**。剩余压缩空间（npz mmap 化、更小模型）记录在案不追
- **复现**：`curl` 拉 bge-small-en-v1.5 官方 `onnx/model.onnx` + `tokenizer.json` 到 `data/onnx_model/`；venv 装 `onnxruntime tokenizers numpy`；`USE_DENSE=1 DENSE_BACKEND=onnx python -m evaluator.local_evaluator`
